# CLAUDE.md

This is a personal Obsidian vault for note-taking, not a software project — no build, test, or lint commands apply.

## Conventions

### Layout

- Every authored note is a `.md` file, wherever it lives: topic notes under `Notes/`, one file per day under `Dailies/` at the repository root (named `YYYY-MM-DD.md`), source summaries under `Knowledge/` (see below). No tagging scheme is in use — keep to this structure unless asked otherwise.
- Create these folders, and `Index.md`, the first time something belongs in them — don't scaffold empty ones up front.
- `Index.md` at the repository root is the vault's map, grouped by topic — a starting point instead of browsing folders directly. Every `Notes/` and `Knowledge/` note gets a wikilink and a short descriptor there; `Dailies/` and `Sources/` are intentionally *not* linked individually, and the index just points at `Dailies/` as the chronological log.
- `.obsidian/` is the Obsidian app's own config (workspace layout, enabled plugins), auto-managed by the app — leave it alone unless asked to change it.

### Sources & Knowledge

- Source material (PDFs of papers, etc.) goes under `Sources/` at the repository root, not alongside the notes — only when there's an actual file to save there.
- Every source gets a summary note under `Knowledge/` at the repository root, named to match (e.g. `Sources/Some Paper.pdf` ↔ `Knowledge/Some Paper.md`), so notes can cite the summary instead of re-parsing a PDF every time. If a PDF/file exists in `Sources/`, the Knowledge note summarizes it and links back to it, and can also cite an official project page or similar if that page has information the PDF doesn't. If no PDF/file can be saved (a webpage, a conversation, general knowledge, etc.), the Knowledge note holds the transcription/summary directly, with a standard Markdown link back to the original URL — nothing goes in `Sources/` in that case.
- `Knowledge/` also holds facts generalized from this vault's own empirical work in `Notes/`, and general background captured from a direct Q&A rather than a document — not just summaries of an external source. Back the general claim with real external sources (docs, an RFC) wherever they exist, even when it's illustrated by a vault-internal example. When no such external corroboration exists and a claim rests solely on this vault's own one-off empirical test, mark that explicitly — at the note or passage level, whichever fits — with a `> [!info]` callout naming the originating `Notes/` file(s), e.g. `> [!info] Generalized from this vault's own notes, not an external source`. A claim with no checkable source behind it is an opinion, not knowledge; this callout keeps that distinction visible instead of letting it blur silently into the same unmarked confidence as an externally-sourced claim.
- Project narrative does **not** become `Knowledge/` just because a `Knowledge/` note is what prompted the work. Implementation logs, build/environment/checkout incidents, status and next-steps, decisions and judgment calls, and "what was tried and why" all stay in `Notes/` (with a `Dailies/` teaser pointing at the note), exactly as they would if the work had started from a `Notes/` topic. The test is the inverse of the one the `extract-knowledge` command applies when it sweeps `Notes/` for general facts: if a passage only makes sense as part of one project's story — or would be stale or useless dropped into an unrelated future project — it's a note, not knowledge. A `Knowledge/` note may still record *where* something surfaced in the vault, but only as the short teaser-plus-wikilink pointer already used for `## Ideas` and `Dailies/` entries, never as a standalone narrative section. Tells that the line's been crossed: a `## Status` or `## Implemented …` heading, a dated "what I did" log, a step-by-step design walk, or first-person "I/we tried …" prose sitting in a `Knowledge/` file.

### Formatting

- `.md` is a file-format choice, not a ceiling on content — these files are opened and rendered by Obsidian, not read as plain text, so any syntax Obsidian understands (wikilinks, callouts, Mermaid diagrams, LaTeX math, tables, embeds) is as available as an ordinary paragraph. Pick whichever the content calls for, rather than defaulting to one out of habit — the goal is whatever's clearest, both rendered in Obsidian and as raw text to an agent reading the file directly.
- Filenames are Title Case with spaces (e.g. `Some Topic.md`), matching Obsidian's default when a note is titled from the UI — except `Dailies/`, which are named by date.
- No level 1 header at the top of a note — the filename already serves as the title in Obsidian.
- Notes and Knowledge summaries cross-reference other vault files with Obsidian wikilinks (`[[Note Name]]`), not standard Markdown links. External URLs (e.g. a Knowledge note linking back to a source webpage) use standard Markdown links instead, since wikilinks only resolve within the vault.
- Don't put machine- or user-specific filesystem paths in a note: where a repo happens to be cloned (`~/Repositories/foo`, `/home/user/foo`), a personal home-directory layout, a sandbox path, or a this-workstation-only system path (`/etc/profile.d/…`, a non-default library directory). They won't exist on another machine and mislead a reader who goes looking. Refer to a repo by name ("the `foo` repo") and to files inside it by their repo-relative path (`packages/api/…`, `docker/worker/Dockerfile`). Still fine to write out: repo-relative paths; canonical tool-defined locations that are identical on every machine and are often the point being made (`~/.claude/CLAUDE.md`, `~/.ssh/config`, `~/.bashrc`, `/etc/hosts`, `~/.cache/pip`); and paths a project defines for itself in committed config (a Dockerfile's `WORKDIR /app`, a `/mnt/data` mount). When a machine-specific detail genuinely carries the finding — a workstation's login-shell profile only running for interactive shells, say — describe it functionally and flag it as local, rather than pasting the absolute path.

## Working here

- Keep notes atomic: one topic per note, linked via wikilinks, rather than one note covering everything.
- Don't add further folders, tags, frontmatter, or other structure on your own initiative beyond the `Notes/` / `Dailies/` / `Sources/` / `Knowledge/` structure described under *Layout*.
- When creating a new file, or adding new content to an existing one, don't derive its format from a template lifted off other files or sections — shape it to whatever best fits the content and situation at hand. If the best fit happens to look like what's already there, that's a fine outcome too; the resemblance should come from the content, not from copying a precedent. This doesn't override anything this file specifies explicitly (e.g. the `## Ideas` section rule below) — follow those specifications as written.
- Create or edit notes automatically whenever a conversation produces something worth keeping — research findings, decisions, empirical results, corrections to earlier conclusions — instead of waiting for an explicit "note this down." Update the relevant existing note if one covers the topic, rather than always creating a new one. Skip purely conversational exchanges that don't add durable information.
- Keep `Dailies/` entries concise — a sentence or two per topic covering what was done and the outcome or status, not a technical write-up. Route technical detail (commands run, exact errors/numbers, root-cause chains, step-by-step fixes) into the relevant `Notes/` note instead — creating one per the rule above if none exists yet — and link to it from the daily rather than inlining the detail there. Same shape as the `## Ideas` rule below: the daily is the teaser, the note is where the coherent write-up lives — don't fragment one finding across both.
- When a note relies on a source, make sure it has a `Knowledge/` summary first — write one per the rules above if it doesn't exist yet — so the note's claims stay traceable back to something without re-parsing a PDF every time.
- Keep `Knowledge/` summaries current: if work turns up something from a source that its summary doesn't yet cover, fold it in at whatever point in the summary it actually belongs — reorganizing existing content if that's what fits — rather than tacking it onto the end. If a summary is found to mismatch or misstate its source, fix it on the spot rather than leaving the error in place.
- The reverse of `extract-knowledge` (which moves general facts from `Notes/` into `Knowledge/`): when a `Knowledge/` note has accreted project narrative, an implementation log, or status/next-steps (per the rule under *Sources & Knowledge* above), move that content into the relevant `Notes/` note — creating one per the atomic-notes rule if none fits — leave the teaser-plus-wikilink pointer behind, and update [[Index]] in the same pass. Do it whenever you notice it, not only when asked.
- When a `Notes/` or `Knowledge/` note is added, renamed, moved, or removed, update [[Index]] to match, in the same pass as the note change rather than as a separate cleanup step.
- Give a topic note a dedicated `## Ideas` section whenever it has proposals that haven't been implemented or tested yet, instead of leaving them scattered inline through the prose — a reader should be able to see everything still open for that topic in one place. Place it after `## Caveats` if the note has one, otherwise right before `## Used by` / `## Sources`. Each entry: the idea in a sentence or two, why it might help, and what's blocking or untested about it. If an idea is long enough to need surrounding context that's already written elsewhere in the note (a dated log entry, a finding it's responding to), link there with a one-line teaser instead of duplicating the prose — don't fragment an already-coherent write-up just to relocate a sentence. When an idea moves from proposed to implemented/tested, move it out of `## Ideas` into wherever the rest of that finding lives (a dated entry, a "Confirmed working" section, etc.) rather than leaving a stale entry behind.
- When writing a new `Knowledge/` note, check whether the source cites any other source that already has a `Knowledge/` note, and record that citation (wikilink to the existing note) in the new one. Don't reverse-check whether existing sources cite the new one — that's too much work to do proactively for every new source. If a citation between two existing sources turns up incidentally while working in the repo, add it to the citing source's `Knowledge/` note too.

## Syncing

- If the repository has an `origin` remote, sync with it first, before any action in a session — including read-only ones like reading or searching a note, not just before making changes — via `git fetch` and fast-forward `git pull` (or equivalent), so the session starts from the latest content rather than a possibly stale local copy (e.g. after edits from another device).
- If that isn't a clean fast-forward — local has diverged from origin, or uncommitted local changes are in the way — stop and surface it to the user rather than resolving it yourself (merging, rebasing, discarding).

## Committing

- Commit and push automatically after making changes to the vault's actual content — `Notes/`, `Dailies/`, `Sources/`, `Knowledge/`, `Index.md` — don't wait to be asked, and don't leave a session's content edits sitting uncommitted. Group a session's related edits into one commit rather than committing after every individual file change. Push only if a remote is configured.
- This doesn't extend to configuration/meta files — `CLAUDE.md`, `.obsidian/`, `.claude/`, and the like — commit and push those only when explicitly asked.
- Stage only the files the session actually changed; don't sweep in unrelated pre-existing changes sitting in the working tree.
